# Tankard v0.3 notes

To be folded into the README / docs. User-facing changes are in `CHANGELOG.md`.

## Menu-bar extra

- `MenuBarExtra(isInserted:)` with `.menuBarExtraStyle(.window)`. The label is the SF Symbol
  `mug` / `mug.fill` (a template image) plus the upgrade count. The panel lists upgrades
  (hammer icon on ones that compile), then Upgrade all (opens the window and the upgrade
  sheet), Open Tankard, Check now (`brew update` + re-read, same as ⌘R) and Quit.
- It reads the same `AppStore` as the window, so the same cache and the same refresh.
  `MenuBarSummary` (TankardAppModel) is the count model.
- Settings → General: "Show Tankard in the menu bar" (default on). With it on,
  `applicationShouldTerminateAfterLastWindowClosed` returns false, so closing the window
  keeps the icon and background checks.

## Background checks and notifications

- Off by default. Turning on "Notify me about new upgrades" is the only moment Tankard calls
  `UNUserNotificationCenter.requestAuthorization`. If macOS says no, the toggle turns back
  off and the pane says where to change it.
- `BackgroundChecker` wakes at least every 5 minutes; `BackgroundSchedule` decides when a
  check is due: last check + N hours (1–48, default 6), never sooner than 2 minutes after
  launch; a check missed during sleep runs at the next wake-up. When an upgrade or refresh
  is running it retries in 15 minutes.
- A check is `brew update` through the FIFO queue, then the normal status read.
- `UpgradeNotificationDiff`: one key per upgrade, `<package id>@<version it would go to>`.
  The first check after turning notifications on only records the baseline. Afterwards a
  notification is posted only when keys appear that weren't in the last set (a newer version
  of a known upgrade counts as new); a set that only shrinks posts nothing. The baseline is
  kept in UserDefaults (`notifiedUpgrades`) and not updated when a check fails.
- Under `swift run` (no app bundle) notifications are skipped: `UNUserNotificationCenter`
  needs a bundle.

## Launch at login

`SMAppService.mainApp.register()` / `unregister()`. The toggle shows the real status
(`requiresApproval` → "Waiting for approval in System Settings → General → Login Items").
Not verified end to end (it would change login items on a shared Mac). Expect it to work
with the Developer ID build; with an ad-hoc build macOS may refuse or forget the
registration, since the login item is tied to the code signature.

## Compile warnings (one classification)

- `CompileClassifier` (TankardCore, `BuildPlan.swift`) answers "bottle or compile?" for an
  upgrade (`upgradeHasBottle`) and for a Discover entry (`CatalogEntry.bottle`). The
  upgrade list, the upgrade sheet's plan page, the menu bar and Discover all use it.
- `BuildTimeEstimating` is the hook for a future formula → seconds map ("about N min").
  `NoBuildTimeEstimates` is the only one used; `BuildTimeTable` is the shape a JSON file
  would decode into. Nothing is fetched or bundled.
- Upgrade sheet: when any selected upgrade compiles, it opens on a plan page with every
  package marked bottle or "No bottle: will compile from source" and a "Skip packages that
  would compile" checkbox. When nothing compiles it starts at once, as in v0.2.
- The Upgrades filter has a "Skip packages that would compile (N with bottles)" button.

## Discover: bottled first (owner request)

- Intelbrew mode now reads each formula's `bottle do` block and `depends_on` lines from the
  tap's `.rb` file while indexing (`FormulaScanner`; no Ruby is run, same as v0.2's `desc`).
  So every formula's bottle is known before any `brew info`: the count on the chip is real.
  On the Intel VM (8,732 formulae) the scan finds 5,344 with a bottle that macOS 14 Intel can
  pour: 554 on intelbrew-core, the rest Homebrew's ghcr.io bottles (sonoma, older macOS, or
  `all`) that the fork keeps. Tankard counts both as "Has Intel bottle", because both pour.
  (The owner's example "566 of 8,732" matches the Intelbrew-only count; say if the chip
  should count only intelbrew-core bottles.) For the 30 rows of a "node" search, the scan
  agreed with `brew info` 30 of 30.
- Cost, measured on the VM in a release build: the scan adds ~50 ms; the whole index (list
  files, read heads, desc, scan) is ~0.35–0.40 s for 8,732 formulae, about the same as v0.2's
  index. Debug builds are several times slower (the README's 0.41 s was measured before the
  scan). `IndexBench` (env `TANKARD_BENCH_TAPS`) times it.
- Chip: "Has Intel bottle (X of Y bottled)" | All. On by default in Intelbrew mode, off in
  normal mode ("Has bottle"). It hides formulae known to compile; unknown ones and casks stay.
- Ranking: within one relevance tier, bottled → unknown → compiles. Relevance still wins
  (an exact name match that compiles stays on top).
- Detail pane: orange box "No Intelbrew bottle yet. Installing compiles from source, which can
  take a long time on older Macs." plus "+N dependencies also compile: …". The walk follows
  runtime deps of bottled formulae and runtime + build deps of compiling ones, skips installed
  ones, and ignores deps it can't find. `on_linux` blocks are skipped; `on_arm` and
  `on_intel` aren't told apart (slight overcount).
- Install becomes "Install (compiles)" and asks first (a sheet with the exact command).

## Build times from Intelbrew (owner request)

- `BuildTimeSource` (TankardAppModel/BuildTimes.swift) reads
  `https://github.com/d4rkwyng/intelbrew-core/releases/download/metadata/build-times.json`,
  schema 1: `{"schema":1,"generated_at","measured_on","formulae":{name:{median_seconds,
  samples,last_seconds,last_version}}}`. It is the `BuildTimeEstimating` the compile
  warnings use.
- **Network: the second request Tankard makes itself, Intelbrew mode only** (the first is
  Discover's formulae.brew.sh in normal mode). Fetched only when a compile warning is shown
  (upgrade plan, Upgrades list row, detail pane, Discover detail), never in normal mode, and
  cached 24 h in `~/Library/Caches/net.mindtricks.tankard/build-times.json`. A 404 (the
  builder replaces the asset daily), any error, bad JSON or another schema means "no new
  data": the cached copy stays in use, and Tankard asks again at most once an hour.
- A formula not in the file, or with no positive time, has no estimate (never zero). The
  median is used (else the last build), rounded **up**: "at least ~24 min on the Intelbrew
  builder" (hours from 90 min). Never a precise number: older Macs are slower.
- The asset isn't live yet (first builder run tomorrow), so the real URL hasn't been
  fetched; tests use a fixture with a fake fetch, and demo mode a bundled illustrative file
  (`Resources/Demo/demo-build-times.json`).
- This goes in the README's *Network* section when the docs are folded.

## Cleanup

- Toolbar trash button (and View → Clean Up…). The sheet runs `brew cleanup -n` off the queue
  (read-only), `brew --cache`, and `du -sk <cache>` concurrently.
- `CleanupDryRun.parse` reads brew's `Would remove: <path> (<size>)` lines (also
  `(N files, size)`, broken links, empty directories) and the summary line `==> This operation
  would free approximately X of disk space.` (brew prints it only when non-zero). Sizes are
  brew's units (powers of 1000).
- The Intel VM's brew exits 1 there: homebrew/core is an untrusted tap under brew 7, so
  `cleanup -n` prints ~3,400 "tap formula is not trusted" warnings, one Error, and no summary
  line. Tankard then shows its own sum of the items, labelled as such, plus brew's error.
- "Clean up" runs `brew cleanup` through the queue with the live log.
- Fixtures (read-only captures, home directory renamed to /Users/you):
  `Tests/TankardCoreTests/Fixtures/arm64-cleanup-n.txt` (this Mac),
  `sonoma-intelbrew-cleanup-n.txt` (the VM).

## Replace with bottle

- Eligible: formula, receipt says `poured_from_bottle: false`, installed version == current,
  no upgrade pending, not HEAD, and the current version has a bottle this Mac can pour.
- Command: `brew reinstall --force-bottle --formula <tap>/<name>`. Both flags were checked
  in `brew reinstall --help` on this Mac (brew 7.0.14-13) and on the Intel VM (7.0.14), and
  in brew's source: `--force-bottle` bypasses the "installed with options / build from
  source" checks (formula_installer.rb `pour_bottle?`) and fails with "--force-bottle passed
  but X has no bottle!" if there is none. Ask mode is skipped without a TTY (stdin is
  /dev/null), so no `--yes` is needed.
- Label: "Intelbrew bottle available" in Intelbrew mode when the bottle URL is on
  intelbrew-core, else "Bottle available". Filter chip "Bottle available" with Replace all.
- On the VM, vim is the one eligible package. On this arm64 Mac's fixture, blake3 and pkgconf.

## App Management (owner request)

- Only cask upgrades and cask uninstalls trigger it (`AppManagement.modifiesApps`). Formula
  operations, installs and Replace with bottle never do.
- The gate is on in the real app (`Dependencies.live`) and in demo mode; unit tests opt in.
- First use: before the first cask upgrade/uninstall, the sheet explains; "I've done this" or
  "Not now" both remember it (`appManagementExplained`) and run what was asked.
- After a failure: each cask step's output is checked by `AppManagement.isPermissionBlock`
  (brew 7.0.14's own "does not have App Management permissions" messages from
  cask/staged.rb, install_steps.rb and cask/quarantine.rb; "prevented from modifying apps";
  "Operation not permitted" on an /Applications path). The sheet then offers one retry
  through the queue; a retry that fails again doesn't reopen it.
- No real failure output was captured (that would mean modifying an app); the matcher's
  test strings are brew's source messages and the usual rename/mv shapes.
- Deep link: `x-apple.systempreferences:com.apple.preference.security?Privacy_AppBundles`.
  On this Mac (macOS 27.2), `open` with it exits 0 and launches System Settings, and the
  Privacy & Security extension's `TCCServiceList.plist` lists `revealElementKeyName`
  `Privacy_AppBundles` for `kTCCServiceSystemPolicyAppBundles`. The screen was locked, so
  the opened pane itself wasn't seen. If opening fails, Tankard falls back to Privacy &
  Security.
- TCC permissions for an ad-hoc signed app are tied to that build's code hash, so every
  rebuild needs the toggle again; a Developer ID build keeps it across updates.
- Demo: `TANKARD_DEMO=arm64 TANKARD_DEMO_APPMGMT=1` (the sheet), `=fail` (cask steps fail
  once with brew's message, then succeed on the retry).

## Release notes

- `CHANGELOG.md` (Keep a Changelog). `Scripts/changelog-section.sh X.Y.Z` prints a section
  and exits 1 if it is missing or empty; `--self-test` checks the extraction.
- The release workflow runs the self-test, builds the notes (intro line with "Signed with
  Developer ID and notarized", the section, the install/upgrade commands) and passes them as
  `body_path:`. A tag without a CHANGELOG section fails before anything is signed.

## Demo and snapshot switches added

| variable | effect |
|---|---|
| `TANKARD_DEMO_UPGRADE=plan` | open the upgrade sheet on its plan page |
| `TANKARD_FILTER=upgrades\|source\|newer\|bottle` | Installed filter on launch |
| `TANKARD_DEMO_CLEANUP=1` (`TANKARD_DEMO_CLEANUP_RUN=1`) | open Cleanup (and click Clean up) |
| `TANKARD_DEMO_REPLACE=1` | replace the selection with a bottle |
| `TANKARD_DISCOVER_ALL=1` | Discover's bottle chip off |
| `TANKARD_DEMO_INSTALL_CONFIRM=1` | open "Install (compiles)" for the Discover selection |
| `TANKARD_DEMO_APPMGMT=1\|fail` | App Management sheet / failure path |
| `TANKARD_SNAPSHOT_VIEW=menubar\|settings\|about` | snapshot that view instead of the window |
| `TANKARD_MENUBAR=0` | hide the menu-bar icon for this run |

Demo runs and snapshot runs use throwaway settings, never the real UserDefaults.
`SET=v0.3 Scripts/screenshots.sh OUT_DIR` takes only the v0.3 shots.
